## この後半で入れたもの

### 1. トークン消費のエージェント別按分（「残量 × 指揮系統」）

- `TranscriptParser.spend(_:)` を新設。**`contextTokens` とは別物**：あちらは「今どれだけ読んでいるか」のスナップショット（出力を数えない）、こちらは「どれだけ使ったか」の累積（出力も数える）
- 重みは公式の価格比 **入力1 : キャッシュ書き1.25 : キャッシュ読み0.1 : 出力5**（全モデル共通）。**レートリミットの実際の計算式は非公開なので代理指標**。`Transcript.swift` の1箇所にまとまっている
- チップに `opus-5 37 62%`。1%未満は出さない。詳細に実数（相当量）
- **バグ修正込み**：`.context` がセッション単位でしかキーを持たず、サブエージェントの文脈量が親の雪だるまに混入していた。`agent == session` の行だけが雪だるまを動かすようにした

### 2. 設定に「連携」を足した（機能が到達不能だった）

`launcherEnabled` は `@AppStorage` で宣言されているだけで**切り替える UI がどこにも無かった**。既定オフなので「起こす」ボタンが永久に出ず、`inputs` が常に空 → 送信も永久に無効、という状態だった。⌘, の設定に「表示」「連携」の2セクションを作って解決。

- `claude` が見つからないときに理由が画面に出る
- パス欄は打鍵ごとにログインシェルを起こさないよう 600ms のデバウンス
- キー文字列は `Cockpit.launcherEnabledKey` / `claudePathKey` に一元化（2箇所に書くと片方だけ直したとき黙ってずれる）

### 3. 停止（割り込み）

`{"type":"control_request","request_id":"…","request":{"type":"interrupt"}}` を stdin に流す。
**プロセスは殺さない**——SIGTERM で落とすとセッションごと終わって続きが送れなくなる。

### 4. stdout を読む（①）

**役割を厳密に分けてある。混ぜると同じ発言が二重に出る：**

| 出どころ | 担当 |
|---|---|
| **transcript** | **確定した過去**。メッセージ・チップ・カードは全部これ。他人が端末で回しているセッションに効く唯一の経路なので置き換えない |
| **stdout** | **今この瞬間だけ**。書きかけの文字、ターンの開始と終了、割り込みの受領、エラー。確定メッセージは作らない |

`Launcher.parseStreamLine(_:)` が1行 → `StreamEvent` の純関数（p0 のコンパイル対象なので検査で守れる）。

### 5. 自分の発言を出す（②）

`user` 行から人間の言葉を拾う。`TranscriptParser.humanText(from:)` として切り出してある。
除外：`tool_result` だけの行／`toolUseResult` を持つ行／`isMeta` の行（**行の直下と `message` の中の両方**を見る）。
窓では人間が右、モデルが左。

## 「司令塔との窓口」として潰した握り潰し（重要）

門（`Gate`）で決めた「答えを書けなかったら必ず欄に出す。黙って消えると司令塔が待ち続ける」と同じ規律を、会話窓にも通した。**ここを緩めないこと。**

1. **`result` を無条件に「終わった」にしていた** — 認証に落ちても上限に当たっても実行中にエラーが出ても「終わった」としか出ず、理由が消えていた。`is_error` と `subtype` を見て `.turnFailed(理由)` に分けた。`subtype` が `"success"` 以外は失敗として扱う（知らない値が来る前提）
2. **`control_response` の `still_queued` を見ていなかった** — 押したのに全部は止まっていない場合に「受領」と出るところだった。残件が 0 でなければ `launchError` に出す
3. **その逆の誤報** — `cancelled > 0`（＝取り消せた件数＝**成功の印**）で警告を出す実装になっていて、完璧に止まったときに「全部は通らず」と嘘をつくところだった。止まり損ないを示すのは `stillQueued` だけ

既存のバグも2つ直した：**stderr を終了時まで読んでいなかった**（`--verbose` で 64KB を超えると `claude` がブロックして帰ってこない）／**ハンドラを外していなかった**（プロセス終了後も残る）。

## 意図的にそうしている（バグに見えるが直さないこと）

- **`share` の分母は「表示中のチップ」ではなく「そのセッションの全履歴」**（畳んだ分・消した分も含む）。畳んだあと残りが 5% / 3% と出るのは正しく、「多く食ったのは畳んだ側」と読める。表示中だけに揃えると 5% が 50% に化けて犯人を誤認する。`clearsDoNotRenormalizeShare()` で固定してある
- **送信できるのは AT22 が起こしたセッションだけ**（今のところ）。端末で開いているセッションに `--resume` で割り込むと同じ transcript を2プロセスが書くため。**③で緩める予定**（下記）
- **`extractLines` を `private` にしない**。行の取りこぼしは「たまに発言が抜ける」としか見えず、窓口では致命的なので検査から叩けるようにしてある

## ③で使う予定の解（調査済み）

**「履歴から再開」は成立する。** 「2プロセスが同じ transcript を書く」問題は**動いているセッション限定**で、AT22 は `~/.claude/sessions/<pid>.json` を読んでいるので**どのセッションが今生きているかを既に知っている**。

- 今**動いていない**過去のセッション → `claude --resume <id>` で再開して会話を続ける。衝突しない
- 今**動いている**セッション → 一覧では読み取り専用として出し、入力欄を塞ぐ

Claude Code の公式ドキュメントも `claude -p --resume <session-id>` を「既存セッションに追加のプロンプトを送る」用途として案内している。

## 調べて確定した外部事情（構想ノートの前提を覆す）

### レート残量は statusLine から取れる（ログイン不要）

Claude Code は statusLine コマンドの stdin に JSON を毎ターン渡し、その中に：

```
rate_limits.five_hour.used_percentage  /  .resets_at
rate_limits.seven_day.used_percentage  /  .resets_at
```

Pro/Max 契約者にだけ、セッション最初の API 応答の後から出る。**サービスにアクセスしていない**（Claude Code が自分の持っている数字を手渡しているだけ）ので、資格情報も要らず規約にも触れない。
実装するなら、AT22 が statusLine コマンドとして自分（か小さなヘルパー）を登録し、受け取った JSON を `memory/` 配下に書いてアプリ側がそれを読む——**門とまったく同じ「ファイル経由でやりとりする」型**。

⚠ `~/.claude/settings.json` への書き込みが要るので「Claude Code に干渉しない」がまた1つ削れる。**自動で書き換えず、README に1行の設定例を載せて手動にする**のを推す。

### 他のツールがやっている「ログイン連携」は規約に触れる

Anthropic の[消費者向け利用規約](https://www.anthropic.com/legal/consumer-terms)：

> サービスへのアクセスを「bot、スクリプト、その他を問わず、自動化された、あるいは人間によらない手段」で行ってはならない。ただし **Anthropic API キーを使う場合、または明示的な許可がある場合を除く**
> アカウントのログイン情報、API キー、アカウント認証情報を他者と共有してはならない

| 方式 | 判定 |
|---|---|
| claude.ai の `sessionKey` cookie | ✗ APIキーを使わない自動アクセス |
| `~/.claude/.credentials.json` の OAuth トークンを借りる | ✗ 同上（`claudeusagewin` 等がこれ） |
| **API キー（従量課金）** | ○ 規約が明示する唯一の抜け道 |
| **ローカル JSONL の集計** | ○ サーバーに触っていない。AT22 は既にこれ |
| **statusLine の stdin** | ○ Claude Code が手渡してくる |

**AT22 は配布物なので、sessionKey 方式は入れない。** README の「AT22 は API キーも OAuth トークンも保存しない」が売りであり、OSS では読者がコードで確かめられる主張になっている。

### GitHub は OAuth できる（Anthropic とは事情が違う）

GitHub の **Device Flow は `client_secret` 不要**（公式ドキュメントに明記）。公開リポジトリに client_id を置いても問題ない。
ただし利用者の選択は **`gh` CLI に乗る**方式：`claude` を起こしているのと同じ形で `gh` を叩き、AT22 はトークンを一切持たない。

## まだ実測していないもの（推測で書いた箇所）

このプロジェクトは全部実測で決めてきたが、以下だけは**ドキュメント記載の形で書いてある**。実データを見たら規則を足すこと。

```bash
# stdout の stream-json が実際に吐く型
echo '{"type":"user","message":{"role":"user","content":[{"type":"text","text":"1+1は"}]}}' \
| claude -p --verbose --input-format stream-json --output-format stream-json --include-partial-messages \
| jq -c '{type, subtype, event_type: .event.type, delta: .event.delta.type}' | head -30

# transcript の user 行が自分の発言をどう持っているか
jq -c 'select(.type=="user") | {content_type: (.message.content|type), first_block: (.message.content[0].type? // "plain")}' \
  ~/.claude/projects/*/*.jsonl 2>/dev/null | sort | uniq -c | sort -rn | head
```

特に `humanText(from:)` は、コマンド出力やシステムが差し込む行が人間の発言として混ざる可能性がある。**混ざるより落とす**方に倒してあるので、逆に「送ったのに出ない」が起きたらここを疑う。
