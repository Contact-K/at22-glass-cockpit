# AT22 Glass Cockpit

Claude Code が今どのファイルを読み書きしていて、サブエージェントが何体どう動いているかを見るための macOS アプリ。

バイブコーディングでは、開発の速度に人間の理解が追いつかなくなる。AT22 は Claude Code が残す transcript を読んで、エージェントの動きとコードの変化を1枚のキャンバスに出す。

## 既定では読むだけ

AT22 は初期状態では **読み取るだけ** で、

- ファイルを書き換えない（**例外は記憶DBだけ**。後述）
- Claude Code の動作に一切干渉しない（フックも設定も触らない）
- ネットワークに接続しない。何も外部に送らない
- **セッションを起こさない**（連携は既定オフ。後述）

他人の作業ログを扱うソフトなので、ここは仕様として固定している。

**記憶DBだけは書く。**壁打ちモードで人間が手を入れた分を `~/.claude/projects/<プロジェクト>/memory/` 配下へ保存する。書き込みはこの1箇所に限られ、置き場の外へは弾く。コードにも transcript にも触らない。門（後述）の答えも同じ置き場・同じガードを通る。

**連携を有効にすると、`claude` / `codex` / `grok` を起こす。**設定で明示的に有効化した時だけ、AT22 はエージェントのセッションを起動できるようになる。その時も：

- **AT22 は認証情報を一切持たない。**API キーも OAuth トークンも保存しない。起こすのは**あなたが既にログイン済みの CLI**（`claude` / `codex` / `grok`）で、通信するのはそのプロセスであって AT22 ではない
- Claude Code は stream-json、Codex は `codex exec`、Grok は ACP（Agent Client Protocol、`grok agent stdio`）で話す。どれも同じ会話欄・同じ盤面に出る。ACP は Gemini CLI や OpenCode なども話す共通の口
- Claude Code を起こす時のセッションIDは AT22 が採番する（`--session-id`）。transcript の在り処が確定するので、起こした先をそのまま画面で追える。Codex / Grok は相手が返したIDを台帳（UserDefaults）に残し、アプリを閉じても続きに繋げる
- CLI の場所はログインシェルに訊いて突き止める。見つからなければそのエージェントの起動UI自体が出ない
- AT22 から起こした Claude Code は、道具の承認を AT22 に訊く（`--permission-prompt-tool stdio`）。Lv.2 は道具ごとに全部、Lv.3 は編集以外を、画面右上の承認の板で許可・書換・却下する。書き換えて許可すると、**書き換えた入力の方が実行される**。サブエージェントの起動（Agent ツール）はどの段でも訊かれないので、そこは今まで通り門が止める
- 人間の承認なしにファイルを書き換える段（Lv.4 / Lv.5）を選ぶ時は、一度だけ確認が入る。Grok は Lv.4 / Lv.5 の時だけ `--always-approve` で起こし、それ以外はあなた自身の既定の権限モードに従う（`grok agent` に段を細かく渡す口が無いため）

第三者依存はここでも増えない（`Foundation.Process` だけ）。

読む先は3つ。`~/.claude/projects/` 配下の transcript と、`~/.claude/sessions/` 配下のセッション状態（Claude Code 自身が書く「動いているか・承認待ちか」）と、**稼働中セッションのプロジェクトディレクトリのソース**（依存グラフを作るため。読む拡張子とスキップするディレクトリは `Sources/AT22/Structure.swift` に列挙してある）。どれも読むだけで、開いて中身を出すことはしない。

端末で起こしたセッションが承認ダイアログで止まると、司令塔の箱が琥珀色の枠になり「承認待ち · 直前の作業」と出る。フックは使わない（Claude Code がセッション状態に書く値を読むだけ）ので、どのサブエージェントが待っているかまでは出ない。

## 見えるもの

**最上段：進行表**

計画段階で積まれたタスクが順に並ぶ。何が来るかを先に見せ、始まったものは枠が脈打ち、終わったものからグレーアウトしていく。ピルをクリックすると計画時に書かれた詳細が読める。

```
完了 16件   ✓ Phase I: 砂時計ジェスチャ  ▶ Phase J を切替中   ・全体ビルド確認
```

未完了は全部出し、完了は直近3件だけ残して残りは件数に畳む。実測で1セッションに200件積まれることがあるため。この帯は「クリア」では消えない。

**タスク一覧（⇧⌘T）**

計画したすべてのタスクを見返す窓。進行表（キャンバス最上段）は完了済みを3件までに切っているのは横に伸びないようにするためで、こちらは逆に**完了済みも畳まずすべて出す**。読み取り専用で、編集・追加・削除はできない——それは Claude Code 側の `TaskCreate` / `TaskUpdate` が担う。

絞り込み4種：**すべて**（全タスク）・**未着手**・**進行中**・**完了**。transcript から `TaskCreate` と `TaskUpdate` を拾って組み立てているので、入力元は進行表と同じ。

**上段：エージェント**

役割・モデル・労働量（ツール呼び出し回数）を階層で表示する。オーケストレーターを回すと指揮系統がそのまま出る。

```
司令塔  fable-5  70
  └ 起動25 読取11 検索10

    W4: 統合・ビルド修正   haiku-4.5  94  終了
      └ 編集33 読取23 ビルド21
    Phase 5 Sonnet レビュー sonnet-5  25  終了
      └ 読取13 編集7 git6
```

親から子へ伸びる破線の上を、**A4 の縦横比をした小さな紙**が流れる。紙には渡した指示が書いてある（呼び出し時の description。MCP のワーカーなら渡したプロンプト）。素の文字を浮かせると背後の線やカードに紛れて読めないので、地を持たせてある。全文はチップを押した先で読める。

2行目には、動いている間は「今していること」、止まっていれば「してきたこと」の内訳が出る。実測でツール呼び出しの45%はファイルに紐づかない作業（検索・ビルド）なので、線では表せない部分がここに出る。

`読取` は Read ツールと、中身を出す Bash（`cat` / `head` / `tail` / `wc` / `diff` / `less` / `more` / `open`）の両方を数える。分けると「何度も読み返している」が2つに割れて順位から消えるため。`ls` は「何があるか探す」行為なので `find` と同じ検索側。待機（`sleep`）と進行表の帳簿づけは労働量に数えない。実測で後者は司令塔の労働の17.5%を占め、本当の作業を順位から押し出していた。

**下段：ファイル**

触られたファイルがディレクトリごとのカードに並ぶ。

- **書き込み量は 点 → 下線 → 虹 の順に足していく**
  - 1–9行 … 左端の四角1個
  - 10–99行 … 四角2個 ＋ 細い下線
  - 100行以上 … 四角3個 ＋ 太い下線
  - 上位2% … 四角3個 ＋ 二重下線 ＋ 文字の色が循環する（母数は**100行以上書かれたファイル**。1本でもあれば必ず1件は虹になる）

  量そのものは**固定寸法の四角**が持つ（下線だけで表すとファイル名が長いほど大きく見える）。下線はその上に重ねる印
- **右端の縦の丸 = 参照回数**（全エージェントの合計）。下のフラグと同じ数で埋まりきる
- 書かれた瞬間に光の帯が名前の上を1回流れる
- 書き込み中は文字ごとに波が走る

数字はセルの中に出さない。ファイル名と幅を取り合ううえ、桁が増えるほど名前が削られるため。**セルをクリックすると内訳が出る** — 誰が何回読んだか、何時にどのエージェントが何行増減させたか。

**カテゴリの色分け**

各セルの左端に幅3ptの帯が出て、そのファイルの役割を示す。6分類：**実装**（Swift など）・**検査**（test / spec / selfcheck を含むファイル）・**ノート**（md など）・**設定**（json / yaml など）・**資材**（png / mp4 など）・**他**（`.other` は帯なし）。

状態（書き込み中・読み取り中・フラグ）の色とは別の場所で語るので競合しない。判定は `Sources/AT22/Category.swift` の純関数で、パス文字列だけで決まる——ファイルシステムには一切触らず、同じ入力に必ず同じ出力を返す。

凡例は画面右上に出し、**今セッションに出ているカテゴリだけ**を並べる。6色すべてが出ることは稀。

**線**

| 線 | 意味 | 向き |
|---|---|---|
| 実線 | 書き込み | エージェント → ファイル |
| 実線 | 読み取り | ファイル → エージェント |
| 破線 | 指示 | 親エージェント → 子エージェント。**指示を書いた紙**が線の上を流れる |

構造モードの本体は**各ファイルが「何をするやつか」**。一覧のセルはファイル名だけで、説明は**クリックした先の解説画面**に置いてある（一覧に2行入れると密度が落ち、作業モードとセルの寸法も揃わなくなる）。

```
呼ばれている 2                                          呼んでいる 1
  □ ContentView  ┈┈╮        …/str8/                   ╭──→ □ S8Tokens
  □ DayView      ┈┈┤     ┌──────────────┐             │
                   ├────→│ TaskItem.swift│─────────────╯
関連ノート 1        │     └──────────────┘
  □ 企画書.md    ┈┈╯
                          タスクの実体。全画面がここを読む

                       ┌────────┬────────┬────────┐
                       │定義した型│ 被参照  │直近の編集│
                       │   3    │   46   │  +87   │
                       └────────┴────────┴────────┘
```

人が書いた説明があればそれを出す。無ければ**そのファイルが宣言している型**に落とす。実測で Swift 364本のうち、説明が取れたのが約半分、残りは型一覧、どちらも空になるのが5%（`extension` だけのファイルや設定ファイルで、名前自体が役割を語っているもの）。

左右の名前はどれも押せて、そのファイルの解説画面に移る。

説明の拾い方は2つに絞ってある。**ファイル名と完全に同じ名前の型に付いた `///`** か、**import 直後の本物のファイルヘッダ**。緩めると別のものを掴む——前方一致まで許すと `Cockpit.swift` が `CockpitMode` の説明を、`// MARK:` の先まで見ると `Transcript.swift` が先頭 enum の説明を、それぞれ「ファイルの役割」として出してしまう。Xcode が自動で入れるヘッダ（ファイル名・プロジェクト名・Created by）も落とす。

**依存は線で敷かない。** 48セルに数十本を交差させると目で追えないので、関係の出し方を2段にしてある。

- **ホバー** … 関係のあるファイル（呼んでいる先と呼ばれている元の両方）が色づき、無関係は沈む
- **クリック** … そのファイルの解説画面が重なる。左＝呼ばれている元と関連ノート、中央＝そのファイル、右＝呼んでいる先、を矢印で結ぶ

`import` では引けない。Swift の単一モジュールにはファイル間の import が無く、`import Foundation` しか出てこないのでグラフが空になる（madge / pydeps 系を採らなかった理由）。代わりに**どのファイルが宣言した名前を、どのファイルが使っているか**で引いている。単一モジュールでも TypeScript でも Python でも同じ規則で効く。

解説画面には説明の全文と、**定義した型の数 / 被参照の数 / 直近の編集行数**が出る。行数や「他のファイルが実際に使っている名前」まで見たいときは、**作業モードで同じセルを押す**（そちらは書き込み履歴と依存の一覧を出す）。

**壁打ちモード**

左＝**材料**（人が持ち込む素）、右＝**記憶DB**（エージェントと人間が相互に書く）。ノートを押すと**さらに右に md の編集欄**が開く。

```
┌─ 材料 48 ────────┐ ┌─ 記憶DB 5 ─────────┐ │ 前提                    │
│ 企画ノート        │ │ ● 前提      project │ │ sessions/HANDOFF.md     │
│ 過去の計画        │ │ ▸ sessions/         │ │ ─────────────────────── │
│ README            │ │   ● 引き継ぎ progress│ │ # 残タスク              │
└──────────────────┘ │   ▸ 7e04693d/       │ │ - 凡例の作り直し        │
                      │     ● この回の計画   │ │                         │
                      └─────────────────────┘ │ ```state                │
                                               │ stage: implement        │
                                               └─ md のまま編集できる ───┘
```

**入れ子はフォルダで作る。**リンクで結ぶ案は捨てた——線が交差して読めなくなるうえ、リンクは書き手の気分で増減して構造が安定しない。ディレクトリなら人間もエージェントも同じものを見る。

```
memory/
  PROJECT.md              前提・計画全体の仕様
  sessions/
    HANDOFF.md            セッション全体のメモ（引き継ぎ用）
    <セッションID>/
      *.md                セッションごとのメモ
```

並びは**寿命の長い順**（前提 → 引き継ぎ → セッションごと）。完了した進捗（`` ```state `` の `stage: done`）は件数に畳む。

**吹き出しではなく編集欄**にしてあるのは、読むだけでなく**人間も書く**ため。エージェントが書いたものに人間が手を入れ、それをまたエージェントが読む——相互に積んでいくのがこの DB の使い方で、開いて閉じる吹き出しでは形が合わない。整形せず md のまま出すので、書いた内容と保存される内容がずれない。

保存は**一時ファイルに書いてから rename、直後に読み返して確かめる**（構想ノートの判断の踏襲）。人間とエージェントが同じファイルを書くので、壊れた状態を残さないことが要る。編集中にエージェントが書き換えた場合、こちらの未保存分は潰さない。

書式は新しく作らず、Claude Code が既に書いている形をそのまま使う。

```
---
name: at22-shipped-v0-1-0
description: v0.1.0 を公開済み…      ← 1行要約
metadata:
  type: project | feedback | reference | user | progress
  originSessionId: 7e04693d…         ← どのセッションが書いたか
---
本文
```

構想ノート③の「記憶DB＋**企画書清書**」のうち、**清書は入っていない**。断片から文章を起こすのは LLM の仕事で、アカウント連携後の回に置いてある。

**フラグ（橙）****フラグ（橙）**

同じエージェントが同じファイルを3回以上読み、一度も書いていない場合に立つ。「実装ワーカーが仕様書を繰り返し参照している」状態に気づくためのもので、参照を司令塔経由に変えるなどの判断材料になる。

実 transcript 2478組の分布から決めた値で、この条件に当てはまるのは全体の1.4%。参照回数だけで判定すると「今まさに編集中のファイル」が毎回引っかかって使い物にならないため、編集ゼロの条件を付けている。

**右端の丸とフラグは母集団が違う。**丸は全エージェントの合計、フラグは (エージェント, ファイル) 単位。別々のエージェントが1回ずつ読むと丸は埋まりきるがフラグは立たない（「同じ相手が何度も読み返している」を見るための条件なので、そこは分けてある）。

しきい値は **⌘,（設定）** で 2〜6 回に変えられる。セル右端の丸もこの数で埋まりきるので、変えると両方が同時に追従する。

**止まった指示（門）**

司令塔がサブエージェントを起こす直前に人間が口を挟むための仕組み。作業モードで、出どころのチップから伸びる線の上に**紙が止まったまま**現れる。紙の頭には待たせている長さが出る。

```
[司令塔]┈┈┈┈┌───┐┈┈┈┈           押すと右の欄が開き、
            │ 12秒 │  ← 止まった紙   許可／却下／書き換えて発行
            │▤▤▤▤│                  の3つで答える
            └───┘
```

**止めているのは AT22 ではない。**AT22 は Claude Code に干渉しないので、司令塔が自分から待ちに入り、AT22 が置いた答えで抜ける。

```
司令塔:  memory/gate/<id>.md を書く → until [ -f <id>.verdict ]; do sleep 2; done → 従う
AT22 :  門を見せる → 人間が答える → memory/gate/<id>.verdict を書く
```

書き込みは記憶DBと同じ置き場・同じガードを通る。AT22 が書ける範囲は増えない。

**どこで止めるかは承認モードで決まる**（ツールバー）。指示ごとの判断ではなく、段で決まる。

| Lv | 名前 | 止める指示 | 起こす時の `--permission-mode` |
|---|---|---|---|
| 1 | 壁打ち | —（指示を出さない） | `plan` |
| 2 | 隣で見てる | 全部 | `acceptEdits` |
| 3 | 気にかけてる | 高リスクだけ | `acceptEdits` |
| 4 | 任せてる | 止めない | `bypassPermissions` |
| 5 | 留守番 | 止めない（無人） | `bypassPermissions` ＋ `--bg` |

Lv.2 と Lv.3 の `--permission-mode` が同じなのは意図的で、**段の違いは門が持つ**。`--permission-mode` が決めるのは「人間に訊かずに何を触れるか」の方。

値は `memory/gate/LEVEL` に書かれる。**司令塔も同じファイルを読む**ので、アプリの設定ではなくファイルが正。

視点のモード（作業／構造／壁打ち）とは別軸。表示名が衝突するので、承認モードの側には Lv 番号が付く。

**雪だるま（文脈の膨らみ）**

タブ帯の右端。長引いたセッションで推論が鈍るのは時間ではなく**文脈の量**で起きるので、`message.usage` の実測（`input` ＋ `cache_read` ＋ `cache_creation`）で育てる。器の大きさは変えず、下から雪が積もる。自動圧縮（`compact_boundary`）で溶ける。

実測1セッションで 39k → **997,520** まで伸び、圧縮で 15,178 に落ちていた。窓の大きさはモデル名からは決められない（1M 版でも `message.model` は `claude-opus-5` としか書かれない）ので、200k を超えて動いていること自体を 1M 版の証拠にする。

| 段階 | 窓の何割 | 出るもの |
|---|---|---|
| 文脈 軽い | 〜50% | — |
| 文脈 育ち中 | 〜70% | — |
| 文脈 重い | 〜85% | 区切って引き継ぐか、圧縮を挟む頃 |
| 文脈 警報 | 85%〜 | 推論が鈍りやすい。引き継いで新しいセッションに移す |

**これはハルシネーションそのものの検知ではない。**出力の正しさは AT22 からは見えない。鈍りやすい状態に入ったことを、鈍ってから気づく前に見せるための目安。切れ目の3つの数は `Sources/AT22/Snowman.swift` にまとめてある。

**バグ修正**：サブエージェントの文脈量が親セッションの雪だるまに混入していた。メインセッションの行だけが雪だるまを動かすようにした。

**トークン消費の内訳**

チップ右肩に、モデル名と労働量（ツール呼び出し回数）に加えて **「そのセッションの合計消費のうち何割を食ったか」** が出る。`opus-5 37 62%` の3つ目の数字。1% 未満は表示しない（合計が 0 なら「0%」が並ぶのを避けるため）。押すと内訳を詳細に表示。

**雪だるまとは別物**——雪だるまは「今どれだけ読んでいるか」のスナップショット（`input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens`、出力を数えない）で、こちらは「どれだけ使ったか」の累積。1ターンぶんのすべての消費を数える：入力 × 1.0 + キャッシュ書き × 1.25 + キャッシュ読み × 0.1 + 出力 × 5.0。

重みは公式の価格比（全モデル共通）。ただし **レートリミットの実際の計算式は非公開なので、あくまで代理指標**。ずれていたら `Sources/AT22/Transcript.swift` の `spend(_:)` の1箇所を変えるだけで全画面に反映される。

分母は「表示中のチップ」ではなく「**そのセッションの全履歴**」（畳んだ分・消した分も含む）。意図的にそうしてある。「非アクティブを消す」で古いエージェントを落としたあと、残ったチップが 5% / 3% と出るのは正しい——「今見えている分はセッション全体の1割しか食っていない＝多く食ったのは畳んだ側」と読める。ここで表示中だけに揃えると、その 5% が 50% に化けて、犯人でないものを犯人に見せてしまう。代わりに、畳んだあとは表示中の share の合計が 1.0 未満になる。

**これができるのは AT22 だけ**。ローカルの transcript を集計するツール（`jq` など）は総量なら取れるが、指揮系統を持たないので「その 40% のうち 25 ポイントはこのサブエージェントが食った」まで言えない。チップが階層構造で並んでいるから出せる情報。

**メッセージ窓（⇧⌘M）**

モデルが書いた言葉。キャンバスが「何をしたか」を出すのに対し、こちらは「何を言ったか」。これまで AT22 は `tool_use` しか見ていなかったので、ここは一画面も出ていなかった。

**思考の本文は残らない。**実測で全12セッション458件すべて `thinking` は空で、`signature` だけが記録されている。出るのは「いつ考えたか」だけなので、既定では畳んである。

窓の下から**割り込める**。ただし送れるのは **AT22 が起こしたセッションだけ**——人が端末で開いているセッションへ `--resume` で割り込むと、同じ transcript を2つのプロセスが書くことになる。起こしたセッションは stdin を開いたまま持っているので、そこへ1行流す。

## 動作要件

- **macOS 15 以降**
- **Apple Silicon**（Intel Mac には対応しない）

> **macOS 15 / 16 の実機では未検証。** 開発と動作確認は macOS 26 で行っている。
> macOS 15 を対象にビルドが通ること、および使用している API がすべて macOS 15 以下で導入されたものであることは確認しているが、実機で動かしてはいない。
> 15 や 16 で問題が出た場合は Issue で報告してほしい。必要なら最低バージョンを引き上げる。

## 開発

自己チェック（SwiftUI 非依存・ターゲット外）:

```
swiftc -parse-as-library Sources/AT22/Transcript.swift Sources/AT22/Cockpit.swift \
  Sources/AT22/CockpitLayout.swift Sources/AT22/Structure.swift \
  Sources/AT22/Category.swift Sources/AT22/Memory.swift Sources/AT22/Gate.swift \
  Sources/AT22/Launcher.swift Sources/AT22/Snowman.swift \
  Sources/AT22/Backend.swift Sources/AT22/CodexLauncher.swift \
  p0-selfcheck.swift -o /tmp/p0check && /tmp/p0check
```

**SwiftUI 非依存のファイルを足したら、この行にも足すこと。** 足し忘れると
`cannot find type ... in scope` で落ちる（`Backend.swift` と `CodexLauncher.swift` で一度やった）。

見え方を画像に焼いて確かめる:

```
swift run AT22 --shot /tmp/cockpit.png 1440 900            # 筐体（外枠）
swift run AT22 --shot /tmp/board.png --board               # 盤面だけ
swift run AT22 --shot /tmp/x.png --transcript <path.jsonl> # 実データを流し込む
swift run AT22 --shot /tmp/x.png --gate                    # 門を1つ立てた状態
swift run AT22 --shot /tmp/x.png --board --mode structure  # 構造／壁打ちの盤面
```

`--shot` は窓を開かずに PNG を1枚吐いて終わる。**`TimelineView` と `ScrollView` の中身は
`ImageRenderer` が組まないので、盤面は `--board` の方でしか写らない**（外枠は `--shot` の方）。
`Menu` / `Toggle` / `TextField` も焼けないので、そこは黄色い箱になる。

実 transcript を渡すとリプレイして検査する:

```
/tmp/p0check ~/.claude/projects/<プロジェクト>/<セッションUUID>
```

配布物の作成:

```
./package.sh 0.1.0 --dry-run   # 証明書が無くても組み立てまで確認できる
./package.sh 0.1.0             # 署名・公証・DMG まで
```
